# session-contract spec 0.1

Status: **0.1**. Schema, event model, and verdict table. Adapter input formats: [0.1-adapter.md](./0.1-adapter.md).

Language of this spec: English. Chinese summary lives in the repository README.

## 1. Position

session-contract is an **acceptance** protocol for one human–agent working session.

| Protocol | Job |
|---|---|
| [AHP](https://github.com/DeepJudge-Agent-Handoff-Protocol/agenthandoffprotocol) | Move objective + sampled context + resources between agent apps |
| A2A accountability / MCP receipts | Cross-org intent, acceptance, execution **non-repudiation** |
| **session-contract** | Human–agent **done-ness**: contract, generated evidence, verdict claim |

It does not move threads. It does not sign receipts. It does not replace a harness loop or a live Stop hook.

A 0.1 checker MUST be useful on a **single** dsh (or later Claude Code) session without any second runtime: flag overreach, incompleteness, and suspected spin from logs. That standalone value is the spec’s only leverage. A spec with no useful checker dies; a useful checker may later be absorbed.

0.1 checkers MUST NOT set `outcome: pass` from model text. `outcome: pass` exists in the schema so 0.1.1 `goal_check` can fill it without a breaking change. The YAML key `goal_check` is **reserved and ignored** in 0.1.

## 2. Pack layout

One directory is one pack. These four names are normative:

```text
<pack>/
  contract.md
  evidence.ndjson
  evidence.ndjson.sha256
  verdict.md
```

Other files in the same directory are allowed (build artifacts, exports) and MUST be ignored by a 0.1 checker.

`evidence.ndjson` is the only evidence. Any “summary” in `verdict.md` MUST be derived from that log. Hand-written session stories are non-conformant.

### 2.1 Line endings and hashes

`contract.md`, `evidence.ndjson`, and `evidence.ndjson.sha256` MUST be written as UTF-8 with **LF** newlines (`\n` only).

A sidecar parser MUST accept CRLF when *reading* `evidence.ndjson.sha256` (strip a trailing `\\r` per line). That tolerance does not apply to hash inputs.

`contract_sha256` is SHA-256 of the **on-disk bytes** of `contract.md`. If those bytes contain CR (`\\r`), the digest will not match an LF-normalized editor view. A mismatch is a **reject** (invalid pack), not a silent rewrite. That is intentional.

## 3. `contract.md`

The file is Markdown for humans. A checker MUST ignore prose. `goal` is required inside the YAML block; a missing `goal` makes the pack invalid.

A checker MUST parse **exactly one** fenced block:

````markdown
```yaml
session_contract: "0.1"
# … machine subset …
```
````

If the block is missing, duplicated, or not the YAML subset below, the pack is invalid (checker exits non-zero; no verdict claim).

The fence body MUST be a **restricted YAML subset**: scalars, sequences, and mappings only. Anchors, aliases, and tags are forbidden. Unknown keys in the mapping MUST be ignored (forward compatible), except that `goal_check` is reserved (§1). Missing required keys → invalid pack.

### 3.1 Machine subset (YAML)

```yaml
session_contract: "0.1"          # required
goal: string                      # required; one-line done condition
writable_roots:                   # required; absolute paths; empty list = no writes
  - /absolute/path
capabilities:                     # required; omitted key = deny
  fs.read: allow | deny
  fs.write: allow | deny          # allow means only under writable_roots
  exec: allow | deny
  network: allow | deny
redundant:
  n: integer                      # required; consecutive redundant calls that trip suspected_spin; >= 2
forbidden:                        # optional; human-only in 0.1; not checked
  - scan_home
# goal_check: reserved for 0.1.1; ignored in 0.1
```

Notes:

- There is no `ask` in 0.1. Approval UX is harness-specific. The checker only sees what **happened**. If a denied capability appears on a `tool_call`, that is overreach.
- `forbidden` is documentation in 0.1. Do not encode tool names here; names differ across harnesses.
- `writable_roots` entries MUST be absolute. Relative roots → invalid pack.

### 3.2 Path matching (normative)

Before compare, normalize a path `p`: replace `\\` with `/`, then lexically resolve `.` and `..` (no symlink policy in 0.1).

A path `p` is **under** root `r` iff, after both are normalized:

```text
p == r  ||  p.startsWith(r + "/")
```

So `/home/rchua/GO` does **not** match `/home/rchua/GO2/src`.

`session_contract.write_paths[]` entries MUST be absolute in the log. An adapter MUST resolve relative write paths against the session cwd *before* emit. A 0.1 checker MUST NOT guess cwd.

### 3.3 Capability classes (normative)

Judgement is by **capability**, never by tool display name.

| Class | Meaning | Typical harness names (informative) |
|---|---|---|
| `fs.read` | Read file contents or list directories | `read`, `Read`, `ls` via exec is `exec` not `fs.read` |
| `fs.write` | Create, edit, delete, or move files | `edit`, `Write`, `str_replace_editor` |
| `exec` | Spawn a process / shell | `bash`, `terminal`, `run_command` |
| `network` | Leave the machine or hit the network | `web_fetch`, `WebSearch`, `mcp_sse` |

An adapter MUST map each harness tool to **one** primary class. If a tool does both (e.g. `bash` curling the network), 0.1 maps it as `exec`. Overreach for `network` then requires `session_contract.network: true` on the event.

`fs.write` overreach: the call’s capability is `deny`, **or** a listed write path is not under any `writable_roots` entry (§3.2). Missing `write_paths` is **not** overreach; see §6.2 warning.

## 4. Evidence log

### 4.1 File

`evidence.ndjson`: UTF-8, one JSON object per line, no pretty-print, LF line endings. Adapters generate it. Humans do not.

JSON values on an event MUST be only: string, boolean, integer (no fractional part), array, object. **No floating-point numbers, no `null`.** This keeps `canonical` stable (`1e-7` vs `0.0000001` is undefined in 0.1).

`ts` values MUST be RFC 3339 timestamps in UTC, with `Z` suffix (example: `2026-08-20T01:00:00.000Z`).

### 4.2 Event kinds

`kind` is one of: `start` | `tool_call` | `tool_result` | `end`.

Align names with [OpenTelemetry GenAI](https://opentelemetry.io/docs/specs/semconv/gen-ai/) where we record a tool:

- `gen_ai.operation.name` = `execute_tool` on `tool_call` / `tool_result`
- `gen_ai.tool.name` = harness tool name (string)
- `gen_ai.tool.call.id` = harness call id
- Do **not** put full arguments or results in OTel-style content fields by default. 0.1 stores **hashes and short digests** only.

session-contract adds:

| Field | Where | Meaning |
|---|---|---|
| `session_contract.capability` | `tool_call` | One of §3.3 |
| `session_contract.network` | `tool_call` | Optional boolean; true if this exec also used the network |
| `session_contract.arguments_sha256` | `tool_call` | SHA-256 of canonical JSON arguments (§4.5) |
| `session_contract.result_sha256` | `tool_result` | See digest definition below |
| `session_contract.write_paths` | `tool_call` | Absolute paths this call intends to write; see §6.2 |
| `session_contract.progress` | `tool_result` | Optional boolean; adapter asserts the world moved. Default: inferred (§6.2) |

**`digest` (normative):** SHA-256 of the adapter’s recorded result body as UTF-8 bytes, lowercase 64-hex. Do not hash a truncated UI preview. The body MAY be text or the canonical JSON of a structured harness value (see the adapter). Empty body → digest of zero bytes.

**`result_sha256` (normative):**

```text
result_sha256 = SHA-256( canonical( { "isError": <bool>, "digest": <hex> } ) )
```

`isError` is true when the harness marked the tool outcome as error (including deny/block). `canonical` is §4.4.

### 4.3 Required shape

**`start`** (exactly one, first line):

```json
{
  "kind": "start",
  "ts": "2026-08-20T01:00:00.000Z",
  "contract_sha256": "<sha256 of contract.md on-disk bytes>",
  "harness": "dsh",
  "session_id": "optional-opaque"
}
```

**`tool_call`:**

```json
{
  "kind": "tool_call",
  "ts": "2026-08-20T01:00:01.000Z",
  "gen_ai.operation.name": "execute_tool",
  "gen_ai.tool.name": "bash",
  "gen_ai.tool.call.id": "call_1",
  "session_contract.capability": "exec",
  "session_contract.arguments_sha256": "<hex>",
  "session_contract.write_paths": []
}
```

**`tool_result`:** SHOULD follow its `tool_call` with the same `gen_ai.tool.call.id`. A `tool_call` with no matching `tool_result` is a **dangling call** (crash/SIGKILL mid-tool). The pack remains valid; see §4.6 and §6.2.

```json
{
  "kind": "tool_result",
  "ts": "2026-08-20T01:00:02.000Z",
  "gen_ai.operation.name": "execute_tool",
  "gen_ai.tool.name": "bash",
  "gen_ai.tool.call.id": "call_1",
  "session_contract.result_sha256": "<hex>",
  "session_contract.progress": false
}
```

**`end`:** SHOULD be the last line. **Absence of `end` does not invalidate the pack** (killed sessions are the ones most worth auditing).

```json
{
  "kind": "end",
  "ts": "2026-08-20T01:00:10.000Z",
  "stop_reason": "user | model | error | abort"
}
```

No other `kind` values in 0.1. Extra JSON keys on an event MUST be ignored.

### 4.4 Hash chain

Let `canonical(value)` be:

1. Recursively sort object keys.
2. UTF-8 JSON with no space after `:` or `,`, and no other insignificant whitespace.
3. Integers in decimal form without exponent or fraction.
4. Arrays keep order.

RFC 8785 is not required. There is **no** per-event `canonicalizer` field in 0.1. All adapters MUST use this default.

Apply `canonical` to each event object **without** the keys `hash` and `prev`.

- `prev` of the first event is 64 zero hex digits.
- `hash` of an event is `SHA-256(prev || "\n" || canonical(event))` as lowercase hex.
- Each event MUST include `prev` and `hash`.

`chain_tip` is the `hash` of the **last event in the file** (the `end` event when present; otherwise the last `tool_call` / `tool_result` / `start`).

`evidence.ndjson.sha256` is two ASCII lines, LF-terminated when written:

```text
<sha256-of-file-bytes>  evidence.ndjson
chain_tip  <hex>
```

A reader MUST treat a trailing `\\r` on each sidecar line as optional (CRLF tolerance). The file-bytes digest is still over the ndjson as stored.

`verdict.md` MUST quote this `chain_tip`. Changing any log byte breaks the file hash; inserting a line without fixing `prev`/`hash` breaks the chain.

0.1 does **not** sign. Hashes only.

### 4.5 Argument canonicalization

`arguments_sha256` is SHA-256 of `canonical(arguments)` as defined in §4.4, applied to the tool argument object (or other JSON value) the adapter recorded. Two calls with the same capability and the same hash are “identical arguments” for §6.2.

### 4.6 Truncated logs

A log is **chain-valid** when: `start` is first, every `prev`/`hash` verifies, and the sidecar file-bytes digest matches.

A chain-valid log **without** `end` is still a valid pack. The checker MUST emit a claim and MUST add `incomplete.truncated` only (not `incomplete.goal`). Dangling `tool_call`s do not fail chain validation.

## 5. `verdict.md`

### 5.1 Two axes (normative)

A session is not a single enum.

| Axis | Values | Meaning |
|---|---|---|
| **outcome** | `pass` \| `incomplete` | Checker view of the **goal**. 0.1 default is `incomplete`. |
| **compliance** | `compliant` \| `overreach` | Did any event violate the YAML capability / writable_roots rules? |

**Spin is not a terminal state.** Checker MAY set `suspected_spin: true` as an evidence feature when §6.2 matches.

### 5.2 Authority split and effective verdict

Exactly **one** fenced YAML block in `verdict.md`. The checker writes the claim fields. The human **appends** `accept` and optional `note` to that same block (the only reading that stays “exactly one fence”).

| Actor | May write |
|---|---|
| Checker | `role`, axes, `suspected_spin`, `chain_tip`, `contract_sha256`, `reasons[]` |
| Human | `accept: true \| false`, optional `note` |

Checker MUST NOT set `accept`.

**Effective verdict** = claim ⊗ `accept`:

| `accept` | Meaning |
|---|---|
| *absent* | **Unpublished.** Tools MUST NOT treat the pack as accepted or rejected. |
| `false` | **Rejected pack.** Human refuses the session; claim axes stay on disk for audit. |
| `true` | **Published `pass`.** Human publishes the session outcome as `pass`, even when the claim `outcome` is `incomplete`. Claim `compliance` is unchanged. |

Reading `incomplete` + `accept: true` without this rule looks contradictory. With this rule it is the 0.1 success path: the checker refused to auto-pass; the human attested done-ness.

### 5.3 Claim YAML (inside `verdict.md`)

```yaml
session_contract: "0.1"
role: claim
chain_tip: "<hex>"
contract_sha256: "<hex>"
outcome: pass | incomplete
compliance: compliant | overreach
suspected_spin: false
reasons:
  - code: overreach.network
    call_id: "call_9"
# human appends:
# accept: true
# note: "proxy print matched"
```

0.1 `reasons[].code` values:

| Code | Severity | When |
|---|---|---|
| `overreach.capability` | overreach | `tool_call` class is `deny` |
| `overreach.write_path` | overreach | write path not under `writable_roots` (§3.2) |
| `overreach.network` | overreach | `session_contract.network` is true while `capabilities.network` is `deny` |
| `incomplete.goal` | outcome | `end` is present; 0.1 still defaults `outcome` to `incomplete` |
| `incomplete.truncated` | outcome | `end` is missing. Do **not** also emit `incomplete.goal` |
| `spin.redundant_streak` | feature | §6.2 |
| `warning.unattested_write` | warning | `fs.write` call with missing or empty `write_paths` |
| `warning.unmatched_tool_call` | warning | `tool_call` with no `tool_result` |

Warnings never set `compliance: overreach` by themselves.

Prose after the fence is human-only.

## 6. Decision table (checker claim)

Inputs: parsed YAML contract + chain-valid evidence (§4.6) + `start.contract_sha256` equal to on-disk `contract.md`.

### 6.1 Outcome

0.1 is conservative on `pass`:

| Condition | `outcome` |
|---|---|
| Any `overreach.*` reason | still evaluate completeness separately (axes are independent) |
| No `goal_check` in 0.1 | default **`incomplete`** |
| `end` present | `incomplete` plus `incomplete.goal` |
| `end` missing | `incomplete` plus `incomplete.truncated` only |
| Model or assistant text claiming success | **ignored** |

Shipping `pass` from “the model said it was done” is forbidden. Human `accept: true` is what **publishes** success (§5.2). The checker’s job on this axis in 0.1 is to avoid false pass.

0.1.1 `goal_check` (not specified here) MUST: run on the checker host, emit `derived` events, **append-only** (never rewrite earlier evidence lines), and fold results into the hash chain.

### 6.2 Compliance and spin

Walk events in log order. Pair `tool_call` with the next `tool_result` of the same `gen_ai.tool.call.id`.

**Overreach** (any match → `compliance: overreach`):

1. `session_contract.capability` is `deny` in the contract.
2. A `session_contract.write_paths[]` entry is not under a `writable_roots` root (§3.2). (`fs.write: allow` still overreaches outside roots.)
3. `session_contract.network === true` and `capabilities.network` is `deny`.

**Unattested writes:** if `session_contract.capability` is `fs.write` and `write_paths` is missing or empty, add `warning.unattested_write`. Do **not** treat that as overreach (the checker cannot invent paths).

**Dangling `tool_call`:** add optional `warning.unmatched_tool_call`, **reset** the redundant streak, and continue. Do not invent a result hash.

**Suspected spin** (`suspected_spin: true`, not a third axis):

A **redundant streak** is `redundant.n` or more consecutive **paired** calls where **all** hold:

1. Same `session_contract.capability`
2. Same `session_contract.arguments_sha256`
3. **No state progress**: `session_contract.progress` is false or omitted, **and** `session_contract.result_sha256` equals the previous pair’s result hash

Retries that change the result hash are progress (streak resets). Pagination that changes arguments is not the same `arguments_sha256` (streak resets). Exploration that changes paths or queries resets. Only “same call, same result, again” counts.

This is **post-hoc log analysis**. 0.1 MUST NOT require an in-loop hook to be correct. Live hooks (Claude Code `PostToolUse`, dsh `tools.guard`) are optional producers of evidence, not the verdict.

### 6.3 Combinations (claim only)

| claim outcome | compliance | suspected_spin | Typical reading |
|---|---|---|---|
| `incomplete` | `compliant` | false | 0.1 default; unpublished until `accept` |
| `incomplete` | `overreach` | false | Left the allowed capability set |
| `incomplete` | `compliant` | true | In-bounds but stuck repeating |
| `incomplete` | `overreach` | true | Both |
| `pass` | *any* | *any* | Not produced by a 0.1 checker |

`pass` + `overreach` is allowed as a **schema** combination for 0.1.1. Human `accept: true` publishes pass regardless of claim `outcome` (§5.2).

## 7. Out of scope for 0.1

- Signatures, transparency logs, AHP HTTP, Thread IDs
- Runtime hard-stop (that is a harness plugin, e.g. dsh-repeat-stop)
- Mapping tables for dsh export / Claude Code hooks — see [0.1-adapter.md](./0.1-adapter.md)
- Goal auto-pass from model text; running `goal_check` (0.1.1)
- Symlink following; Unicode path case-folding beyond §3.2
